# rspipe — RealityScan ヘッドレス バッチパイプライン GUI

フォルダを渡す → **index 単位で任意枚数ごとに分割** → 各セットを **Align**（前セットのコンポーネントを引き継ぎ）
→ **最大コンポーネント選択** → **疎点群 / カメラ情報 / コンポーネント を Export** → 次のセット
→ 最後に **全セットを mergeComponents で統合**。

```bash
python K:\realityscan\run_gui.py
```

CLI だけで回すとき:

```bash
python run_batch.py presets\1-mid-1.json --max-sets 2
```

```bash
python run_batch.py presets\1-mid-1.json --dry-run
```

依存は標準ライブラリのみ (Python 3.10 / tkinter)。

---

## 1. 画像セットの作り方（index 単位）

ファイル名は `画像名_index_視点方向`（例 `1-mid_0000_00.jpg`）。**分割もオーバーラップも index 単位**で、
1 つの index に属する全視点は必ず同じセットに入ります（同一 index の 8 方位はカメラ中心が同じで
ベースラインがゼロのため、単独ではアラインできません）。

`Indices per set = 100`, `Overlap indices = 10` なら:

```
set 0 : index   0 - 99     (新規 100)
set 1 : index  90 - 189    (引き継ぎ 90-99 + 新規 100-189)
set 2 : index 180 - 279    (引き継ぎ 180-189 + 新規 190-279)
...
```

### セットの引き継ぎ方 (`Set chaining = component`)

2 個目以降は、**前セットのコンポーネントを import して、オーバーラップ index 以外を
アライン対象から外し、新しい画像だけを追加**します。

```
-importComponent <前セット>.rsalign
-selectImage g/_(0090|0091|...|0099)_/     ← オーバーラップ index
-invertImageSelection                       ← それ以外＝前セットの古い画像
-editInputSelection inpEnabled=false        ← アラインから除外
-add <新規画像>.imagelist
-align
```

**アラインから外した画像は新しいコンポーネントに入らない**ので、セットは太らずに
「オーバーラップ + 新規」で一定のサイズを保ちます。実測（6 index/セット、2 index 重複、
10 セット、pose lock あり）: 全 10 セットが 48/48 = **480/480 (100%)**、
マージ後 **336/336 (100%)**、合計 352 s + マージ 135 s。

import したコンポーネントはそのまま別コンポーネントとして残るため、
`-selectComponent <前セット名>` → `-deleteSelectedComponent` で捨ててから
`-selectMaximalComponent` しています（そうしないと、新規アラインが失敗したときに
古いコンポーネントの方が大きくなって、それをエクスポートしてしまう）。

`Set chaining = images` にすると引き継ぎをせず、オーバーラップ index を
ただの共通画像として各セット独立にアラインします。

### オーバーラップの長さ（5 では足りません）

**同一 index の全視点はリグ中心を共有しています。** `1-mid-2` で実測すると、
1 index 内の 8 視点のばらつきは、次の index までの距離の **0.7%** しかありません。

つまり **N index のオーバーラップは「N×視点数 台のカメラ」ではなく「ほぼ直線上の N 点」**です。
5 index なら 40 枚の画像があっても、幾何的には 5 点の直線でしかありません。
この配置では、2 つのコンポーネント間の相似変換の**スケールがほとんど決まりません**
（直線に沿う方向しか拘束されない）。

`1-mid-2`（67 セット・オーバーラップ 5）で起きたこと:

| セット | マージ | 結果 |
|---|---|---|
| lock あり | `fs=0` | 分裂（最大 6,212 / 10,656） |
| lock あり | `fs=1` | 分裂（最大 6,158） |
| lock あり | 2 段階結合 | 1 個だが index 999 以降が潰れる |
| lock なし | `fs=1` | 1 個だが index 832 以降が **9 倍に伸長** |

pose lock はこの退化を隠します（引き継ぎカメラが前セットと完全に一致するため、
スケールが同一性から決まる）。lock を外すと退化がそのまま出ます。
`1-mid-1` / `1-high` / `1-low` が問題なかったのは lock ありだったからです。

**対策はオーバーラップを長くすることです。** 10 index 以上、直線的に進む撮影では
`chunk_indices` の 4 割程度を目安にしてください。共有区間が長くなればスケールが
それ自体で決まるので、lock も不要になります。

セットあたりの枚数は増えますが、やり直しのコストに比べれば安いです
（`1-mid-2` はこの問題の切り分けだけで 40 時間以上を消費しました）。

### セット境界を覆う（`extra_passes` / `extra_chunk_sizes`）

マージが 2 つのセットを繋ぐ手がかりはオーバーラップだけで、それは短いです。
**大半の接合は成功しますが、数%が失敗します。** 3 バンドを統合したときの実測:

| バンド | オーバーラップ | セット境界 | 壊れた接合 | 境界以外の最大 |
|---|---|---|---|---|
| `1-mid` | 5 | 45 | 1（6.2x） | 1.39x |
| `1-high` | 3 | 25 | 1（7.6x） | 1.39x |
| `1-low` | 3 | 39 | 2（1.9x / 2.0x） | 1.23x |

**109 箇所中 4 箇所（3.7%）**。境界以外は 1.4 倍以下で完全に滑らかなので、
「全体が歪む」のではなく数点で軌跡が切れ、それが全体の破綻として見えます。

GUI「1. Images」タブの *Cover the set boundaries* で 2 つの対策が使えます。

**`Extra offset passes`** — 同じ画像を、ストライドの半分ずらしてもう一度タイリングします。
1 パス目の**すべての境界が 2 パス目のセット内部に入る**ので（実測 25/25）、
細い接点が失敗する場所にセット半分ぶんの太い接点ができます。

**`Extra set sizes`** — 別のサイズでもタイリングします。境界がばらけるうえ、
長いセットは遠くのカメラまで拘束します。ただし境界が互いを外すのは偶然頼みで、
公倍数の位置では一致します。**保証が要るなら offset passes の方**です。

書式は `サイズ:オーバーラップ:パス数` で、後ろ 2 つは省略できます。

| 書き方 | 意味 |
|---|---|
| `15, 35` | 上の Overlap indices と Extra offset passes をそのまま使う |
| `15:5, 40:16` | サイズごとにオーバーラップを指定 |
| `40:16:1` | オフセットパス数も指定 |

**省略はあまり勧めません。** 25 index 用に決めたオーバーラップ 10 は、
15 index なら 3 分の 2、40 index なら 4 分の 1 と意味が変わります。

どちらも**全画像のアラインが 1 パス分増えます**。各パスは独立に連鎖し、
別パスのコンポーネントを引き継ぐことはありません（独立した検証にするため）。
セット名には `_p11` `_s15` `_s40p12` のようにパス名が付きます。
**閉ループはすべてのパスに適用されます**（基準パスだけ閉じて他が開いたままだと、
基準パスの始端・終端の境界を覆うというオフセットパスの目的を果たせません）。

先に試す価値があるのは、**壊れた境界だけを狙ったパッチ**です
（`_smoke/align_patches.py`、`1-mid-2` で最悪の接合残差 24.4 → 3.7 index を実測）。
4 箇所なら 1.5 時間で済みます。全パスを増やすのはその後で構いません。

### オーバーラップの pose lock（既定 off）

`lock the overlap cameras' pose during alignment` を on にすると、引き継いだ
オーバーラップのカメラを `-lockPoseForContinue true` で固定してからアラインします。
48 枚 × 10 セットでの実測:

| | 登録 | 10 セット合計 |
|---|---|---|
| lock なし | 477/480 (99.4%) | 435 s |
| **lock あり** | **480/480 (100%)** | **352 s** |

自由度が減るぶん速く、しかも lock なしで数枚落ちていた 2 セット（index 16–21, 20–25）が
どちらも埋まりました。

#### それでも既定を off にした理由

lock は引き継ぎカメラを前セットの姿勢に固定します。新規画像がわずかに違うスケールで
解けたとき、**その食い違いの逃げ場が固定境界しかなく、段差として現れます**。

セットは 20 index ごとに始まり 25 index 分をカバーするので、各セットの
6 番目（`index % 20 == 5`）が新規画像の 1 枚目 ＝ 固定境界です。`1-mid-2` の実測:

| 位置 | 中央値 | p95 | 最大 |
|---|---|---|---|
| `% 20 == 5`（固定境界） | 1.10x | 2.47x | **11.90x** |
| その他 19 箇所すべて | 0.89〜1.03x | ≤ 1.47x | ≤ 3.02x |

同じ index 84→85 を 2 つのセットで比べると原因がはっきりします。

| セット | 84→85 |
|---|---|
| `0060-0084`（84 を新規として解いた） | 1.05x |
| `0080-0104`（80〜84 を lock して 85 以降を解いた） | **14.74x** |

`0080-0104` の中では、lock 区間の間隔が新規区間の約 1.7 倍になっていました。
同じセットを lock なしで解き直すと段差は消えます（`_smoke/test_lock_off.py`）:

| セット | 境界 | lock あり | lock なし |
|---|---|---|---|
| `0080-0104` | 84→85 | 14.74x | **1.10x** |
| `0220-0244` | 224→225 | 8.18x | **上位 10 位外（< 1.06x）** |

どちらも全区間が 1.0〜1.3x に収まりました。

**これは以前「ずれている」と判断された `1-high` の閉ループ由来の 3.24x より大きい段差です。**

一方で `1-mid-1` / `1-high` / `1-low` では同じ位置の最大が 1.23x / 1.25x / 2.05x と
無害でした。つまり lock が害になるのはアラインのスケールが不安定なデータだけですが、
**事前には分かりません**。速度 2 割と数枚の登録より幾何の連続性を優先して off を既定にしています。
速度を取りたい場合は `_smoke/diag_step_profile.py` で `% 20 == 5` の列を確認してください。

**ただし lock はコンポーネントに保存され、それを import した `-mergeComponents` は
`Invalid or corrupted input data` で即座に落ちます**（実測: 10 コンポーネントすべてで結合ゼロ）。
そのため、パイプラインは**アラインの間だけ lock し、エクスポート前に解除**します。

```
-selectImage g/_(overlap)_/ -lockPoseForContinue true
-align
-selectImage g/_(overlap)_/ -lockPoseForContinue false   ← エクスポート前に解除
-exportSelectedComponentFile ...
```

解除は lock した画像だけに掛けます。`-selectAllImages` で解除しようとすると、
引き継ぎで無効化した未登録の画像が選択に混ざり `-lockPoseForContinue` が
`Invalid or corrupted input data` で失敗します。

**lock した画像自体がアラインで落ちることもあります。** その画像は未登録になるので、
解除の選択に混ざった時点で同じエラーになり、`appQuitOnError=true` のため
**エクスポートを 1 つも出さずに実行全体が終わります**（実測: `1-mid-2_1040-1064` が
200 枚中 160 枚しか登録できず、終了コード `2147942487` で成果物ゼロ）。
未登録の画像を選択から外す手段が `-selectImage` の正規表現には無いので、
パイプラインは**このセットだけを lock なしで自動的に再実行**します。
登録率は多少落ちますが、コンポーネントが 1 つも出ずに index が丸ごと欠けるより確実です。

### 既存コンポーネントの注入（`seed`）

GUI「1. Images」タブの *Seed sets with existing components*。1 行 1 件で、
`<セット> = <.rsalign のパス>` を並べます。`<セット>` はセット番号・セット名・
`first` のいずれか。`#` で始まる行は無視されます。

```
first = K:\realityscan\out\1-mid-1\1-mid_0000-0024\1-mid_0000-0024.rsalign
```

用途は**別々のキャプチャを繋ぐこと**です。同じ場所を高い位置と普通の位置で 2 回
歩いた場合、両者は 1 枚も画像を共有しないので `-mergeComponents` に手がかりが
ありません。2 本目の最初のセットに 1 本目の最初のコンポーネントを渡しておくと、
そのセットのアラインで両者が 1 つのコンポーネントに入り、最終マージが辿れます。

`1-mid-1`（8 視点/index）と `1-high`（11 視点/index、同じ画角 100°）で実測:

| | `1-high` セット 0 | `1-high` セット 1 |
|---|---|---|
| シードなし | 267/275 (97.1%)、843 s | 272/275 (98.9%)、167 s |
| **シードあり** | **469 カメラ**（1-high 271 + 1-mid 198）、1,891 s | **275/275 (100%)**、224 s |

注入した 198 カメラは全部繋がりました。副次的に `1-high` 自身の登録も 267 → 271 に
増え、その効果が連結でセット 1 にも伝わって 100% になっています。

最終判定として `1-mid` 2 個 + `1-high` 2 個の計 4 コンポーネントをマージ:

| | 結果 | 内訳 | 所要 |
|---|---|---|---|
| シードなし | **2 個に分離**（358 と 487） | 358 = 1-mid のみ / 487 = 1-high のみ | 426 s |
| **シードあり** | **1 個（849 カメラ）** | 1-mid 358 + 1-high 491 | 655 s |

実装上の判断:

- **投入は「引き継ぎ画像の無効化」より後。** 連結セットは
  「オーバーラップ index 以外を `inpEnabled=false`」を実行するので、その前に
  シードを入れると一緒に無効化されます。後に入れればシードのカメラは全部
  アライン対象のまま残ります。アライン後は連結元と同様に名前で削除するので、
  `-selectMaximalComponent` がシードを選ぶことはありません。
- **`-selectImage` の index 正規表現はプレフィックス付き。** 従来の
  `g/_(0020|0021)_/` はシードで別キャプチャが混ざると `1-mid_0020_00.jpg` と
  `1-high_0020_00.jpg` の両方に一致してしまいます。現在は
  `g/1-high_(0020|0021)_/` です。
- 全画像が同一キャリブレーショングループに入るので、**注入元と注入先の画角が
  同じである必要があります**（`1-high` は f_35mm 15.1045、`1-mid-1` は 15.1038 で一致）。

> ログの `seed joined N cameras` は「結果カメラ数 − そのセット自身の画像数」なので、
> 注入先自身の登録も増えた場合は実際より小さく出ます。正確な内訳は
> `cameras.csv` のファイル名プレフィックスを数えてください。

## 2. マージ

全セットが終わったあと、各セットの `.rsalign` を 1 つのシーンに import して
`-mergeComponents` します。オーバーラップ index の画像が両セットに含まれているので、
そこで繋がります。

結果は `out_root/_merged/` に、各セットと同じ形式（疎点群・カメラ情報・コンポーネント・プロジェクト）
で出力されます。マージが実質失敗した（最大コンポーネントが入力より増えなかった）場合は
`failed` として理由付きで報告します。

### Features source（既定 `1 use component features`）

`-mergeComponents` の直前に全入力へ `-setFeatureSource` を掛けます。
48 枚 × 10 セット（重複なしの実画像 336 枚）を、**同じ 10 コンポーネントに対して
マージだけ**を切り替えて比較した実測:

| Features source | 登録 | tie points | 平均誤差 | 所要 |
|---|---|---|---|---|
| `-1` 未設定 | 336/336 | 488,741 | 0.5946 px | 287 s |
| **`0` merge using overlaps** | 336/336 | **539,073** | 0.5979 px | **135 s** |

lock なしのコンポーネント（334/336 止まり）でも同じ傾向で、`0` は `-1` の約半分の時間で
tie points が約 10% 増えました。`1 use component features` は `-1` と数値が完全に一致するため、
**RealityScan の既定は `1`** です。`2 use all image features` は最も遅く（301 s）、
点数は `0` に及びませんでした。

`0` が効くのは「連続するセットが必ずオーバーラップ画像を共有している」からです。

**ただし `0` を既定にするのは危険でした。** `1-mid-2`（67 セット・10,656 枚）では、
`0` はマージ結果を 6,212 / 4,605 の 2 コンポーネントに割ってしまいました。
破断部を 1,776 カメラ分またぐブリッジを足しても割れ方は変わらず（6,416 / 4,236 / 156）、
**共有カメラの量ではなく繋ぎ方の強さが足りていない**ことが分かりました。

同じデータを `1` でマージすると **10,645 カメラが 1 コンポーネント**にまとまりました。

| Features source | 結果 | 備考 |
|---|---|---|
| `0` merge using overlaps | 2 コンポーネントに分裂 | オーバーラップ画像だけを見る。速いが弱い |
| **`1` use component features** | **1 コンポーネント** | RealityScan の既定。**これを既定にしています** |
| `2` use all image features | メモリ不足で失敗 | 全画像の特徴を再検出。10,656 枚 × 約 3 万特徴は 96 GB でも足りない |

`0` は 4.4 節のようなテクスチャの豊富なデータでの高速化オプションと考えてください。
`2` は共有カメラを持たないコンポーネントを混ぜるときに必要になりますが、
枚数が多いと `sfmMaxFeaturesPerImage` を下げないと落ちます。

### ブリッジ コンポーネント（`merge.extra_components`）

セット同士が共有するのはオーバーラップ index の数枚だけです。この細い接点は、
**規模が大きくなるとマージ側で繋ぎ損ねることがあります**。

`1-mid-2`（67 セット・10,656 枚）の実例:

- マージ結果が `Component 0: 6,212` と `Component 1: 4,605` の 2 つに割れた。
- 割れ目は index 505。**前向きの視点（00/01/02/07）だけが先に進んで別コンポーネントになり、
  後ろ向きの視点（03/04/05）は index 600 過ぎまで前のブロックに残った**。
  同じ index の 8 方向が 2 つのコンポーネントに分裂した状態。
- 前半分と後半分を繋ぐのは左右の 02 / 06 ＝ 360 カメラの継ぎ目の視点で、
  この区間ではその 2 つが虫食いになっていた。点群も薄い区間（66k〜110k 点、
  他は 200k〜400k）で、継ぎ目のゴーストと低テクスチャが重なっている。

ただし**セット単位では 200 枚すべてが 1 コンポーネント**になっており、
破断部を含む 11 セット（index 440〜664, 1,800 枚）だけを切り出してマージし直すと
**1,776/1,788 = 99.3% が 1 コンポーネント**にまとまりました。8 方向すべてが
index 505 をまたいで繋がっています。つまりデータは繋がるのに、
規模が大きいマージだけが細い接点を取りこぼしています。

対策が `extra_components` です。各セットのコンポーネントに加えて、
**破断部を広くまたぐ 1 つのコンポーネント**を import します。
両側と数百 index 分を共有するので、5 index しかない接点よりずっと素直に繋がります。

```json
"merge": {
  "extra_components": ["K:\\realityscan\\out\\1-mid-2\\_bridges\\bridge_0440-0664.rsalign"]
}
```

ブリッジの作り方は 2 通りで、どちらでも構いません。

1. 破断部をまたぐ範囲を**1 セットとしてアライン**する。
2. 破断部の周辺セットだけを**先にマージ**して、その結果を使う（上の実例はこちら）。

### マージが使えないときのオフライン合成

`1-mid-2` では `-mergeComponents` が 4 通りとも正しい結果を出せませんでした
（1 節「オーバーラップの長さ」の表）。セット単体のアラインは正しいので、
**各セットを共通座標系に載せる相似変換を自分で連鎖させる**ことで合成できます。

```bash
python _smoke/stitch_chain.py <out_root> <出力先> --prefix 1-mid-2 --patches <パッチ置き場>
```

退化を避けるための要点が 2 つあります。

- **回転はカメラの向きから求める。** 位置は直線上の数点しかなく、その軸まわりの
  回転が決まりません。1 index に 8 方向あるので、向きの対応からは一意に決まります。
  規約は `R = Rz(−yaw)·Rx(pitch)·Ry(roll)`（`_smoke/find_euler_convention.py` が
  共有カメラから逆算。残差 0.0487°、次点は 4.52° なので一意）。
- **スケールは index 間移動距離の比の中央値から求める。** 重心からの RMS 比だと
  弱く拘束された区間端に引きずられ、67 接合の連鎖で 4.8 倍のドリフトが出ました。

正しさの検証には `_smoke/diag_scale_chain.py` を使います。セット単体のアラインだけから
基準となる step profile を再構成するので、**どのマージ結果とも独立に照合できます**。
`1-mid-1` / `1-high` / `1-low` はこれで基準と一致することを確認済みです
（誤差 0.01〜0.02）。

残差の大きい接合は `_smoke/align_patches.py` で境界をまたぐ 25 index を単独アラインし、
`--patches` で渡すと A→パッチ→B の経路に置き換わります（共有 40 → 102 枚）。

## 3. マスク

`attach a mask to each image` を on にすると、画像ごとにマスクレイヤーを割り当てます。

- マスク名は `Mask name` のテンプレートで決めます。既定は `{name}.mask.png`
  （`1-mid_0000_00.jpg` → `1-mid_0000_00.jpg.mask.png`）。`{stem}` `{ext}` も使えます。
- `Mask folder` が空なら画像と同じフォルダを見ます。
- 黒 = 無視、白 = 使用（COLMAP と同じ向き）。
- `Used for` は RealityScan の `inpMaskOpts`（既定 = アラインのみ）。

実装は `-selectImage <画像>` + `-setImagesLayer <マスク> mask` を画像の数だけ並べた
**`.rscmd` ファイル**で、`-execRSCMD` から流し込みます。数百枚分をコマンドラインに直接
並べると Windows の長さ上限を超えるためです。パスは引用符付きで出力するので空白を含んでも動きます。

検証: 96% を黒で塗り潰したマスクを 1 枚だけに当てたところ、その画像の特徴点が
**13,027 → 649** に落ち、他の画像は 1 点も変わりませんでした。

> マスクファイルが存在しない画像に `-setImagesLayer` を投げると実行全体が
> `File not found` で落ちます。実在するマスクだけを `.rscmd` に書き出しています
> （`1-mid-1` は 7336 枚中 5117 枚にしかマスクがありません）。

### 360 カメラの継ぎ目（結論: マスクしない）

2 眼の 360 カメラは前後のレンズを**正面から ±90°** の位置で貼り合わせます。
2 つのレンズが同時刻に露光されないと、その付近の被写体が 2 重に写ります。
8 視点・画角 100° の切り出しでは、1 本の継ぎ目が**同時に 3 つの視点**に入ります。

| 継ぎ目 | 真ん中に入る視点 | 端に入る視点 |
|---|---|---|
| +90°（右） | 02（幅の 14.9%） | 01 の右端・03 の左端（各 19.8%） |
| −90°（左） | 06（幅の 14.9%） | 05 の右端・07 の左端（各 19.8%） |

角度が同じでも画素幅は同じになりません（`x = f·tan θ`）。視点の端に来るほど
広い範囲を占めます。生成は `_smoke\make_seam_masks_angular.py`（半角を引数で指定、
既存マスクとの AND を取って出力）。

**それでもマスクしないことを推奨します。**

- 継ぎ目を 10° 分マスクしても平均誤差の改善は **1.3%** に留まり、
  一方でカメラを 5 台失いました。
- より重要なのは、**02 / 06 はリグの前半分と後半分を繋ぐ唯一の視点**だという点です。
  `1-mid-2` のマージが index 505 で前向き（00/01/02/07）と後ろ向き（03/04/05）に
  割れたのは、まさにこの 2 視点が低テクスチャ区間で繋ぎ役を果たせなかったためでした
  （2 節「ブリッジ コンポーネント」）。ここをマスクで削ると、割れやすさは悪化します。

ゴーストは誤マッチを生みますが、`sfmMaxFeatureReprojectionError=2.0` の閾値で
大半は落ちます。継ぎ目の情報を捨てる損失の方が大きい、というのが実測の結論です。

### 4.4 パラメータ掃引の実測（19 構成）

`1-mid-1` で実測した結果です。生データは `_smoke\sweep_results_final.csv`。

**セットサイズ**（オーバーラップ 10、Medium/Medium/ds1、いずれも 300 index スロット）:

| | セット数 | カバー index | セット登録 | セット処理 | マージ | 秒/index |

| 50 index/セット | 6 | 250 | 99.8% | 2093 s | 653 s | 10.98 |
| 25 index/セット | 12 | 190 | 99.8% | 1430 s | 623 s | 10.81 |

画像 1 枚あたりのコストはセットが小さいほど安い（1.15 / 0.87 / 0.60 秒）が、
オーバーラップの占める割合が増えて相殺されます。**マージ時間はコンポーネント数に
ほとんど依存せず、総画像数で決まります**（3 個 710 s / 12 個 623 s）。
どの構成でも最初のセットだけ 2〜4 倍遅い（連結なしでゼロから解くため）。

**1 因子ずつの掃引**（25 index × 6 セット、index 0–99 の同一区間、800 枚）:

| 構成 | セット登録 | マージ登録 | index あたり点数 | 平均誤差 | 秒/index |
|---|---|---|---|---|---|
| 基準 Medium/Medium/ds1 | 99.6% | 99.5% | 11,373 | 0.602 | 9.89 |
| `sfmImagesOverlap=Low` | 99.8% | 99.4% | 12,311 | 0.584 | 12.33 |
| **`sfmImagesOverlap=High`** | 99.3% | 99.25% | 10,951 | 0.613 | **7.06** |
| `sfmDetectorSensitivity=Low` | 98.6% | 98.6% | 9,426 | 0.582 | 8.40 |
| `sfmDetectorSensitivity=High` | 99.5% | 99.5% | 13,528 | 0.598 | 12.34 |
| `sfmDetectorSensitivity=Ultra` | 99.2% | 99.25% | **15,084** | 0.622 | 13.73 |
| `sfmImageDownscaleFactor=2` | 99.1% | 98.75% | 2,394 | 1.149 | 4.74 |
| ds2 × sens High | 98.8% | 99.0% | 2,854 | 1.198 | 5.56 |
| ds2 × sens Ultra | 98.8% | 99.0% | 3,700 | 1.289 | 6.65 |
| ds2 × imgOverlap High | 98.2% | 98.4% | 2,309 | 1.149 | 4.07 |

- **`sfmImagesOverlap` は速度ノブではなく入力の性質の宣言。** Low にすると候補ペアを
  広く探して 25% 遅くなり、High にすると 29% 速くなります。1 index に 8 視点＋連続 index
  というこのデータは高重複なので **High が実態に合っています**。マージ時間は半減。
- **`sfmDetectorSensitivity` は登録率にほぼ効かず、点密度に効く。** Low→Ultra で
  index あたり点数が 9,426→15,084（1.6 倍）になる一方、登録率の最良点は Medium。
  疎点群を濃くしたいときだけ上げる設定です（Ultra は 1.39 倍の時間で点数 1.33 倍）。
- **`sfmImageDownscaleFactor=2` は 2.1 倍速いが点密度が 1/5 に落ちる。** 平均誤差
  1.149 px は半解像度の値なのでフル解像度換算 2.3 px 相当。感度を Ultra に上げても
  点密度は 1/4 までしか戻らず、失われた情報は取り返せません。カメラ位置だけ欲しい
  用途に限れば選択肢になります。

**オーバーラップ**（カバー区間が変わるため登録率と秒/index のみ比較可能）:

| オーバーラップ | カバー index | セット登録 | マージ登録 | 秒/index | スロットあたり |
|---|---|---|---|---|---|
| 5 (20%) | 125 | 99.8% | 99.7% | **9.65** | 0.73 s |
| 10 (40%) | 100 | 99.6% | 99.5% | 9.89 | 0.62 s |
| 20 (80%) | 50 | 99.8% | 99.8% | 13.63 | 0.48 s |

増やすほど画像 1 枚あたりは速くなる（引き継ぎ済みカメラが増えて新規解決が減る）のに、
index あたりでは遅くなります。登録率は 5 でも落ちません。

**組み合わせの確認**（オーバーラップ 5 × `sfmImagesOverlap=High`）:

| | カバー index | セット登録 | マージ登録 | index あたり点数 | 秒/index |
|---|---|---|---|---|---|
| 25×6 overlap 5 / Medium | 0–124 | 99.8% | 99.7% | 12,538 | 9.65 |

| | 値 |

中央値 0.033%・p95 0.11%・最大 1.46%、スケール比 0.9999。false の方が 6% 速く、
`.rsalign` のエクスポートまで含めてこの時間なので、**false を既定にしています**。

> マージは 2 時間近く**ログを一切出さずに**計算し続けます。停滞と見分けるには
> ログではなく CPU 使用率を見てください（このときは 16 コア中 10 コアが稼働）。

### 4.6 セットサイズをさらに小さくしたら（対照実験）

index 0–304（2,440 枚）を固定して、セットサイズと重複率だけを変えた比較:

| | セット数 | セット処理 | マージ | 合計 | 登録 | tie points | 平均誤差 |
|---|---|---|---|---|---|---|---|
| 25 index / 重複 5 | 15 | 1,689 s | 1,281 s | 2,970 s | 2,433/2,440 | 4,012,803 | 0.5729 px |
| 12 index / 重複 3 | 34 | 1,768 s | 1,601 s | 3,369 s | 2,438/2,440 | 4,168,848 | 0.5759 px |

**12/3 は 13% 遅く、品質は実質同一**です。理由は 2 つとも直感に反していました。

- **セット処理の高速化は 25 index 付近で頭打ち。** スロットあたりコストは
  0.563 → 0.547 s と 3% しか下がりません。100/50/25 で観測した超線形性
  （1.15 / 0.87 / 0.60 s/slot）は 25 index 以下では続かず、セットあたりの固定
  オーバーヘッド（プロセス起動・コンポーネント import・プロジェクト保存・
  エクスポート）が支配的になります。index あたりでは重複率が 20% → 25% に
  上がったぶん 5.40 → 5.80 s と悪化します。
- **マージはコンポーネント数にほとんど影響されない。** 15 → 34 個（2.27 倍）で
  マージ時間は 1.25 倍。指数にして約 0.27 です。46 個のマージが 1 枚あたり
  0.985 s まで膨らんだのは、コンポーネント数ではなく**総画像数**（2,440 → 7,336）
  が主因でした。

全測定を合わせた概算モデル: **マージ時間 ∝ コンポーネント数^0.3 × 画像数^1.4**。

全 917 index に当てはめると 25/5 の 3.6 時間に対して 12/3 は約 4.0 時間で、
**25 分ほど損**をします。さらに高速化したいなら、セットサイズではなく
マージ側（総画像数の指数が支配的なので、全体を 1 回でマージせず区間ごとに
分ける）に手を入れるのが正しい方向です。

### 4.7 追いアライン（登録率が足りないセットの再実行）

`retry.enabled` を on にすると、登録率が `retry.min_ratio` に届かないセットに対して
`retry.max_attempts` 回まで `-align` をやり直します。各パスは独立したプロセスで
保存済みの `.rsproj` を読み直すので、閾値に達した時点で打ち切れます。
`retry.drop_minor_components` を on にすると、**最大以外のコンポーネントを全削除**
してから再アラインします。

全 917 index の実行で登録率が 100% に届かなかったセットのうち 5 つで実測
（各 3 パス、閾値 100%、`_smoke\test_retry.py`）:

| セット | 初期構成 | 未登録 | plain | **drop** |
|---|---|---|---|---|
| `1-mid_0840-0864` | [192, 3, 2] | 8 | 192 → 192 (+0) | 192 → **195 (+3)** |
| `1-mid_0000-0024` | [198, 2] | 2 | 198 → 198 (+0) | 198 → **199 (+1)** |
| `1-mid_0480-0504` | [191] | 9 | +0 | +0 |
| `1-mid_0580-0604` | [194] | 6 | +0 | +0 |
| `1-mid_0360-0384` | [195] | 5 | +1 | +1 |

- **効くのは複数コンポーネントが出たときだけ。** 2 例とも `drop` のみが回収し、
  `plain` は 0 でした。単一コンポーネントのセットでは両モードとも基本的に無力です。
- **アラインは決定的ではありません。** 同じプロジェクト・同じ設定でも実行ごとに
  結果が揺れます（`1-mid_0360-0384` は plain では 2 パス目、drop では 1 パス目に
  +1。`1-mid_0580-0604` では 4 カメラ／5 カメラ／なし と回ごとに違う孤立
  コンポーネントが出ました）。ただし揺らぎ由来の回収は +1 程度です。
- **回収率は約 17%**（未登録 30 枚に対して 5 枚）。1 パス 40〜100 秒。
- **改善はすべて最初の有効パスで起きました。** `drop` では 3 例とも 1 パス目。
  `max_attempts` は 1〜2 で十分で、3 回目に価値はありません。

> **`-align` はアライン済みプロジェクトに掛けるとコンポーネントを複製します。**
> `Component 0` の隣に `Component 0 (1)` が生まれ、カメラ数はほぼ同じで点数だけ
> 微妙に違います。エクスポート前に `-selectMaximalComponent` するので成果物は
> 正しいのですが、`drop_minor_components=false` だとパスごとに複製が溜まります。
> on にしておけば次のパスで削除対象になり自動的に片付きます。

### 4.8 マージ手順の比較（6 パターン）

入力を固定（index 0–304 をカバーする 15 コンポーネント、2,440 枚）して、
マージの手順だけを変えた実測。スクリプトは `_smoke\merge_patterns.py`。

| パターン | 所要 | 対 one_shot | カメラ | tie points | 平均誤差 |
|---|---|---|---|---|---|
| **`one_shot`** 15 個一括 | **1,198 s** | 1.00× | 2,433 | 4,012,757 | 0.5730 px |
| `two_stage_g5` 3個×5→5個 | 1,163 s | 0.97× | 2,433 | 4,011,306 | 0.5711 px |
| `one_shot_align` +`-align` | 1,512 s | 1.26× | 2,433 | 4,012,743 | 0.5732 px |
| `two_stage_g3` 5個×3→3個 | 1,581 s | 1.32× | 2,433 | 4,012,249 | 0.5698 px |
| `one_shot_fs1` fs=1 | 1,836 s | 1.53× | 2,433 | 3,762,294 | 0.5697 px |
| `sequential` 1個ずつ14段 | 3,520 s | 2.94× | 2,433 | 4,011,854 | 0.5702 px |

- **手順は結果を変えない。** 6 パターンすべてでカメラ 2,433 台が完全一致、
  tie points は fs=1 を除き 0.04% 以内、平均誤差の幅は 0.6%。変わるのは時間だけです。
- **階層マージは効かない。** 最終段が結局すべての画像を扱うので、1 段目が
  純粋な上乗せになります。最良の g5 でも一括と同等（−3% は測定ばらつきの範囲）。
- **最終段のコストはコンポーネント数で説明できない。** 同じ 2,440 枚に対して
  3 個 → 861 s、5 個 → 656 s、15 個 → 1,198 s と**単調ですらない**（±30%）。
  マージのコストは実質的に総画像数で決まります。
- **`-align` の後追いは無駄。** +26% 払って点数 −14、平均誤差は 0.5730 → 0.5732 と
  わずかに悪化。`mergeComponents` の時点で全体のバンドル調整が済んでいます。
  `merge.align_after_merge` は off のままで構いません。
- **`feature_source=0` は実規模でも正解。** fs=1 は +53% で点数 −6.2%
  （336 枚規模の +81% / −9% と同傾向）。
- **逐次マージは最悪。** 段ごとの所要が累積画像数に比例して伸びるため
  （42 → 83 → 144 → … → 403 s）総和が二次的に効き、2.94 倍になります。

**結論: 現行の一括マージが最適で、手順の工夫による改善余地はありません。**
速くする唯一の方法は「全体を 1 つに統合しない」ことですが、成果物の性質が変わります。

### 4.9 推奨設定と全体の見積もり

`presets\1-mid-1.json` は上の結果を反映済みです:

- `chunk_indices=25`, `overlap_indices=5`
- `sfmImagesOverlap=High`, `sfmDetectorSensitivity=Medium`, `sfmImageDownscaleFactor=1`

- `chain.close_loop=true`（周回撮影なので最終セットが先頭 index を取り込む）
- `merge.feature_source=0`, `merge.force_rematch=false`

実測は 4.5 節のとおり、セット処理 95 分 ＋ マージ 120 分 = **約 3 時間 35 分**でした
（見積もりではマージを 37 分としていましたが、実際は 120 分と 3 倍以上かかりました。
コンポーネント数ではなく総画像数で決まるという小規模での観測は、7336 枚では
線形には伸びませんでした）。

用途別の振り方:

- **疎点群を濃くしたい**: `sfmDetectorSensitivity=Ultra`（点数 1.33 倍、時間 1.39 倍）
- **カメラ位置だけ速く欲しい**: `sfmImageDownscaleFactor=2`（2.1 倍速、点密度 1/5）
- 画角が確定しているので `inpCalibration=2 (Fixed)` にすれば自由度が減って安定・高速化する
  可能性があります（未計測）。

### 4.10 4 つの撮影バンドの実測

同じ推奨設定で通した 4 バンドの結果です。`1-mid-1` 以外は最初のセットに
`1-mid_0040-0064` をシードとして注入し、共通のカメラを持たせています
（バンド同士を後から繋ぐため。1 節「既存コンポーネントの注入」参照）。

| バンド | 画像 | index | 視点 | セット | マージ後の登録 | 所要 |
|---|---|---|---|---|---|---|
| `1-mid-1` | 7,336 | 917 | 8 | 46 | 7,287 (99.3%) | 3.6 h |
| `1-high` | 6,182 | 562 | 11 | 28 | 6,370 (99.8%) | 4.4 h |
| `1-low` | 8,690 | 869 | 10 | 44 | 8,888 (100%) | 8.8 h |
| `1-mid-2` | 10,656 | 1,332 | 8 | 67 | 10,649 (99.9%) ※オフライン合成 | 約 40 h |

登録数がバンドの画像数を超えているのは、シードのカメラが加わるためです。

`1-mid-2` だけ `-mergeComponents` が使えず、`_smoke/stitch_chain.py` で合成しています
（1 節「オーバーラップの長さ」、2 節「マージが使えないときのオフライン合成」）。
成果物は `out/1-mid-2-nolock/_stitched/`。最終的な品質:

| | 値 |
|---|---|
| カメラ | 10,849（うちシード 200） |
| index の連続性 | 8 視点中 6 視点が欠けゼロ、02 が 3 個・06 が 4 個 |
| step profile の変動 | **0.91〜1.10（±10%）** — 他バンドの ±6% に近い |
| 最大の局所段差 | **2.61x**（pose lock 版は 11.90x） |
| 疎点群 | 9,392,243 点 |

弱い接合 8 箇所は `align_patches.py` のパッチで置き換えています。
これにより最悪の接合残差が 24.38 → 3.69 index ステップに下がり、
連鎖のドリフトも解消しました（パッチなしでは前半が 0.48 と 3 割以上縮んでいた）。

**閉ループは無効にしてください。** `1-high` を `chain.close_loop=true` で通したところ、
最終セットが先頭 index を取り込んだ結果、**index 299/300 でカメラ間隔が 3.24 倍に飛ぶ
不連続**が出ました。誤差は輪のいちばん弱い接合部（tie point の少ないセット同士が
出会う場所）に集中します。無効にして通し直すと最大 1.40 倍まで下がりました。
`close_loop=false` が既定です。

**視点方向が増えると 1 セットあたりの枚数も増えます。** `1-low` は 10 視点なので
25 index/セット = 250 枚となり、8 視点の 200 枚より 1 セットが重くなります。
`1-low` が 8.8 時間かかったのは主にこれが理由です。

## 7. RealityScan CLI について調べた事実

実機 (RealityScan 2.2.0.119430) で確認したもの。ベンダのドキュメントには載っていません。

- **`-set` の値はアプリ設定として永続化される。** 前回の実行の値が次回に効いてしまうため、
  `cli.py` の `_settings()` はパイプラインが依存する全キーを毎回明示的に投げ直しています。
- **Export フォーマットは `calexFileFormatId` で固定できる。** `-set` でも
  `<Configuration><entry key="calexFileFormatId" value="{GUID}"/></Configuration>` という
  params.xml でも効きます。GUID は `<install>\calibration.xml` に定義。
- **画像も書き出すフォーマット（COLMAP / transforms.json / OpenCV CSV）は
  `calexExportImages=false` で抑止できる。** 48 枚で 60 MB〜330 MB 変わります。
- **統計は `-printReport` で機械可読に取れる。** ただし変数にはスコープがあり、
  外で使うと `undeclared identifier` でジョブごと落ちます:
  - `componentName` / `componentCamerasCount` → `$IterateComponents(...)` の中
  - `componentPointsCount` → さらに `$ComponentInfo(componentGUID, ...)` の中
  - `componentMeanError` などの誤差 → `$ComponentStats(componentGUID, ...)` の中
  - `imageCount` / `actualComponentGUID` → `$ExportProjectInfo(...)` が必要
- **`-importComponent` したコンポーネントは、ファイル名（拡張子なし）がそのまま
  コンポーネント名になる。** `-selectComponent` で名指しできます。
- **`-lockPoseForContinue` の状態はコンポーネントに保存され、locked なカメラを含む
  コンポーネントを import した `-mergeComponents` は `Invalid or corrupted input data`
  で失敗する。** アラインの間だけ掛けて、エクスポート前に解除する必要があります。
- **`-lockPoseForContinue` は未登録の入力を含む選択に対して失敗する。**
  引き継ぎで `inpEnabled=false` にした画像が選択に混ざらないようにしてください。
- **`-setFeatureSource` の既定は `1`（use component features）。**
  `-1`（未設定）と数値が完全に一致することで確認しました。
- **アラインを無効にした入力は、そのとき作られるコンポーネントに入らない。**
  セット引き継ぎのサイズ制御はこれを利用しています。
- **画像をプロジェクトから削除する CLI コマンドは存在しない**ので、
  コンポーネントの一部だけを切り出すには上の方法しかありません。
- `-detectFeatures` は単体だと `Operation aborted` になることがあります（`-align` は問題なし）。
- `-exportMasks` は `folderPath` と `params.xml` の 2 引数が必要で、片方だけだと
  params.xml として解釈されて失敗します。
- `-printProgress` は `algId fraction elapsed eta #event` を stdout に流します。
- `-headless -silent <dir> -set "appQuitOnError=true"` の組み合わせで、
  今回のワークフローではダイアログは一切出ませんでした。
- **`-load` に相対パスを渡すと、シェルの作業ディレクトリではなく RealityScan 自身の
  それで解決される。** 見つからないまま処理が続き、次のコマンドで無言のまま停止します
  （実測: 2 時間 48 分で CPU 81 秒 ＝ ほぼ停止）。パスは絶対で渡してください。
- COLMAP エクスポートは `colmapDirStructure` が `0` で `sparse/0/`、`1` でファイルと同じ階層。
- **抑制されたダイアログはログに残る。** `Popup suppressed due to silent mode:` の行に
  タイトル・本文・選ばれた既定動作が出ます。既定動作は
  `-set "PUS-<id>=<n>"` で変更できる旨もヒントとして併記されます。
- **マージ時に `sfmFeatureDetectionQuality` をコンポーネント作成時と変えてはいけない。**
  RealityScan は保存済みの特徴を使えないと判断し、**入力を黙って
  `use all image features` に切り替えて再検出します**。メモリは減るどころか増え、
  22,208 枚では終了コード `0xC0000374`（ヒープ破損）で落ちました。
  `feature_source=1` の使用メモリはコンポーネントを作った時点で決まっており、
  マージ時に絞ることはできません。

## 8. 既知の制限

- **並列実行なし。** RealityScan は 1 インスタンスで GPU を使い切るため逐次実行です。
  セット引き継ぎがあるので、そもそも順番に流す必要があります。
- **`run.timeout_min` は経過時間の上限ではなくハング検出です。** CPU を使い続けている
  限りタイマーは再武装するので、マージが何時間かかっても打ち切られません。
  経過時間で切っていた頃、`feature_source=1` のマージが**繋ぎ終えた直後・書き出し前に
  6 時間で殺され**、成果物ゼロで 6 時間を失いました。判定は「1/20 コア未満しか
  使っていないか」で、実測ではハングが 0.008 コア、正常なマージが 8 コアです。
- **マージは全セットを 1 シーンに import する。** セット数が多いとメモリを食います。
  11 セット × 800 枚規模はまだ実測していません（3 セット × 48 枚では 50 秒）。
- **COLMAP の txt / bin。** 歪み補正画像を出すと `sparse/0/*.txt`、出さないと `*.bin` になる
  挙動を観測しましたが、切り替えキーは特定できていません。既存の `K:\data\col\sparse\0` は
  `.bin` なので既定のままで一致します。
- キャッシュ位置の変更 (`appCacheLocation`) はアプリ再起動が要るため未対応。
  ディスクが厳しい場合は「clear cache after each set」を on にしてください。
